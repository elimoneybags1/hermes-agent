# Restore planning capabilities through the Hermes foundation

**Yes: Claude Code and Codex provide planning and delegation behaviors worth bringing into Team, but the strongest first step is to expose capabilities already present in Hermes.** The current boss has Claude’s reasoning, native Hermes memory and context management, and Team’s coordination tools. It lacks convenient access to target-project source, focused exploration helpers, and an explicit plan-to-execution contract. Those gaps limit how well it can investigate a request before assigning work. Keep Hermes as the primary runtime, borrow useful workflow conventions, and make any native Claude Code or Codex integration a bounded specialist under Team’s control. This investigation changed no execution code and measured no planning-quality improvement.

## The transport retained Claude but removed its normal agent workflow

Our implementation still launches **the Claude Code binary with `claude -p`**. It is not a separate raw model API. Team disables its ordinary tools, slash commands, settings, MCP servers and session persistence, supplies the Hermes prompt and conversation, and asks for structured output. Hermes then executes requested tools and continues the conversation. Consequently, native Claude Code planning and subagent behavior does not automatically accompany these calls. ([Team transport](/Users/fullmoney/work/Team/team/claude_transport.py:24), [subscription adapter](/Users/fullmoney/work/Team/team/subscription_gateway.py:34), [programmatic Claude Code](https://code.claude.com/docs/en/headless))

That change does not remove Claude’s ability to reason about a plan. It removes runtime assistance: tools for investigation and delegation, their permissions and lifecycle, and the surrounding planning interface. Copying an instruction file cannot recreate those mechanisms. Conversely, restoring all Claude Code tools inside this transport would introduce another tool loop underneath Hermes and obscure which runtime owns the work. An explicit specialist adapter is a cleaner option when the complete native harness is useful.

## The most valuable features prepare work before committing to it

Claude Code’s Explore and Plan subagents demonstrate the value of **separate contexts for research**: the parent receives findings without carrying every intermediate search and file read. Anthropic also recommends interviewing the user about consequential ambiguities and producing a self-contained specification with affected interfaces, exclusions and verification. Team can adopt that process while preserving your preference to ask only when a decision matters. ([Claude Code subagents](https://code.claude.com/docs/en/sub-agents), [interviewing and specifications](https://code.claude.com/docs/en/best-practices#let-claude-interview-you))

Codex adds a useful distinction between **Plan and Goal**. Planning discovers and agrees on an approach; a goal preserves the desired end state, constraints, verification and stopping conditions while work continues. Its Goals guidance explicitly includes outcome, verification surface, resource boundaries, iteration policy and a blocked stop condition. Team currently has executable checks, but a passing task check should not silently stand in for satisfying your entire request. ([Long-running work](https://learn.chatgpt.com/docs/long-running-work), [Using Goals in Codex](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex))

A living plan should survive a fresh agent session. It should record scope, decisions, assumptions, milestones, dependencies and observed acceptance evidence. The archived Codex ExecPlans recipe is useful as a planning convention, rather than a current runtime dependency or a template to import unchanged. Its autonomy assumptions need adaptation to your decision ownership. ([ExecPlans recipe](https://developers.openai.com/cookbook/articles/codex_exec_plans))

There is also value in a separate completion assessment. Claude Code’s documented `/goal` evaluator reads conversation evidence; it does not independently execute verification. Team could use a similar evaluator to identify unmet acceptance criteria while retaining its actual tests and landing gates. This separates “the worker finished talking” from “we have evidence the user’s objective is satisfied.” ([Claude Code goals](https://code.claude.com/docs/en/goal))

## Hermes already has much of the machinery

The fork includes `delegate_task`, isolated child conversations, result summaries, steering and interruption, and concurrency/depth controls. It also includes a plan-authoring prompt and Kanban task decomposition. **The Team boss currently exposes neither delegation nor the native planning command path.** Its thin interactive wrapper handles exit commands, while its read/list tools are rooted in Team itself rather than the selected attached project. ([Native entry](/Users/fullmoney/work/Team/team/hermes_native.py:69), [file boundary](/Users/fullmoney/work/Team/team/harness_tools.py:43), [Hermes delegation](/Users/fullmoney/work/Team/vendor/hermes-agent/tools/delegate_tool.py:1))

Two boundaries require deliberate implementation. Hermes `/plan` is **prompt-only**: it instructs the agent to investigate and write a plan using existing tools, but installs no read-only permission policy. Delegated children normally inherit parent capabilities, and the public delegation path does not by itself produce a narrowly restricted explorer. Simply enabling delegation would therefore be insufficient. Team should constrain child tools and target paths in host code, including preventing inherited task creation, project mutation and shared skill writes. ([Hermes planning semantics](/Users/fullmoney/work/Team/vendor/hermes-agent/agent/plan_prompt.py:1), [child capability inheritance](/Users/fullmoney/work/Team/vendor/hermes-agent/tools/delegate_tool.py:1803))

The current clarification callback also discards the choices supplied by Hermes’s clarification tool. Improving that interface would let the boss present concrete options instead of only a text question. These are integration gaps in our wrapper, not reasons to replace the Hermes foundation. ([Team clarification callback](/Users/fullmoney/work/Team/team/hermes_native.py:97))

## Add planning helpers without replacing durable workers

I recommend the following implementation order. These are proposed changes, not features implemented by this research.

| Priority | Concrete change | Purpose |
|---|---|---|
| First | Add target-scoped read/search tools and render clarification choices | Let the boss inspect the real project and ask informed questions |
| Next | Adapt Hermes’s plan prompt, with a narrow save tool writing into Team state | Persist scope, decisions, acceptance criteria, ownership and dependencies without granting general writes |
| Next | Add constrained Explorer and Plan Critic helpers through native Hermes delegation | Investigate architecture and challenge missing requirements before dispatch |
| Then | Add a code-enforced readiness transition from plan to executable work | Require suitable acceptance evidence and resolution of consequential blockers |
| Then | Evaluate whole-goal completion and feed planning evidence to the Optimizer | Learn whether planning changes reduce rework and missed requirements |

The **Explorer** should answer a bounded question about code, dependencies or conventions. The **Plan Critic** should look for contradictory interfaces, missing decisions, overlapping file ownership and weak acceptance criteria. Each receives a clear question, relevant constraints, allowed tools, an effort limit and a structured return format. Initially, keep delegation shallow and use it for independent investigations. This follows Codex’s documented preference for read-heavy helper work and summarized returns. ([Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents))

These helpers serve the boss’s planning conversation. A durable implementation worker has a different contract: it owns a deliverable, branch, retries, checks and eventual landing. Keep those workers on Kanban. Team currently rejects boss-created dependencies whose parents have not already passed and landed, so a complete pending task graph still needs separate integration. Transient subagents will not fix that automatically. ([Task creation gate](/Users/fullmoney/work/Team/team/hermes_boss.py:104), [execution and grading](/Users/fullmoney/work/Team/team/run.py:674))

## Native Claude Code or Codex can remain optional specialists

If a particular planning or review task demonstrably benefits from a native harness, Team could dispatch a bounded job to that harness and consume its structured findings. Team would retain the task identity, budget, scope and acceptance authority. Claude Code agent teams are currently documented as experimental and overlap with coordination that Kanban already owns; they are not required merely to obtain useful research helpers. ([Claude Code agent teams](https://code.claude.com/docs/en/agent-teams))

The integration and billing boundary must remain explicit. Claude’s Agent SDK embeds its runtime; it is not an importable collection of planning markdown or an automatically interchangeable subscription transport. Codex SDK/app-server are documented integration routes, while app-server remains experimental and OpenAI’s managed Agents API is separately API-billed. Do not revive examples based on the removed `codex mcp-server` command. Any pilot must verify the local client and approved authentication path without silently switching to paid APIs or cloud execution. ([Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview), [Codex SDK](https://learn.chatgpt.com/docs/codex-sdk), [app-server](https://learn.chatgpt.com/docs/app-server), [MCP server removal](https://learn.chatgpt.com/docs/mcp-server), [Agents API pricing](https://developers.openai.com/api/docs/guides/agents-api/overview))

The practical next change is a **Hermes-backed planning workflow for the boss**, beginning with real project inspection and a persistent goal contract. Evaluate it on representative tasks before adding another runtime. The criterion is better specifications, fewer avoidable retries and stronger acceptance evidence—not the number of agents spawned. Official documentation and local source establish available mechanisms; they do not establish that our proposed configuration will outperform the current one until it is tested.
